ENGINEERING PRINCIPLES (apply at every SDLC step: ideation, planning, building, review, evaluation, iteration)

1. Reuse before you write. Never hand-roll solved problems: authentication/sessions/JWT, OAuth2/OIDC, password hashing, crypto, input validation, routing/HTTP framework, CSRF, rate limiting, security headers, date handling, parsing (CSV/markdown/YAML), logging, email/payment SDKs. Use established, widely used libraries. Custom code is for the product's own domain logic only.
2. Choose mainstream, maintained frameworks/libraries with compatible licenses, a healthy ecosystem, stable releases and low supply-chain risk. Prefer the PREFERRED LIBRARIES list; pick something else only when none fits, and explain why in the design. Do not require that every application use JavaScript or be dependency-free.
3. Match the requested product to the supported stack profiles (React/Angular; Node.js/Express/Fastify/NestJS; .NET/ASP.NET Core; Terraform/OpenTofu) and to installed tooling. State the exact stack in `tech_stack`, include coherent project layout, lockfiles and executable checks, and never silently fall back to a toy implementation when a standard framework is missing.
4. Built-ins count as standard where appropriate: Node standard library, .NET BCL/ASP.NET Core, framework-standard test facilities. Do not add a package for something the chosen framework already does well.
5. Declare dependencies using that stack's package manager: JavaScript engineers list packages on `DEPENDENCIES: express, zod`; .NET changes use reviewed PackageReference entries and a NuGet lock file; IaC pins provider/module versions and commits its lock file. The factory vets npm dependencies; other package managers must use official registries, locked restore and vulnerability checks. Never hand-edit `node_modules` or generated lock content.
6. Every imported package must be declared and locked. Do not import an undeclared/uninstalled package.
7. Libraries that talk to external services (OAuth/OIDC providers, payment, email, cloud) may be wired up, but stay INACTIVE and configuration-driven until the human supplies accounts/credentials (golden rules 3 and 6). Never hardcode secrets; integrations default to disabled.
8. Reviewers reject hand-rolled security-sensitive code when a standard library exists. Evaluators flag it. Iteration planners schedule replacing custom implementations with standard libraries before adding new features.
9. Seek enhancement: if a task would go faster or safer with an existing framework, tool, skill, or MCP server, name it in your output (`tooling_suggestions`) so the factory's tool scout can evaluate it. Never install or run development tools yourself.
